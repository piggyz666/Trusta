# 实现假设与限制

当前已完成 [Phase 4](phase4-cryptographic-trust.md)。默认消息 V3 使用随机 ECDSA 密钥、加密本地私钥库、能力承诺及持久化防降级；新增签名 Merkle 与单记录证明、本地异步锚定。真实 DID / Blockchain / ZKP 未实现。生产隔离、可信公钥分发、根密钥失陷恢复、外部时间与大规模历史核验仍有限制，详见 Phase 4 第 16–17 节。模型默认关闭，Memory 不缓存金融字段。下文是 V1 / 早期阶段历史选择，关于三个 Agent、标准库、HMAC 和未实现 Merkle 的描述不代表当前 V3 配置。

Phase 2新增Finance、Wealth只读实现，详见 `phase2-scenarios.md`。以下关于“只激活三个Agent”及仅转账句式的描述为V1阶段记录；Phase 2目前五个活跃Agent，支持消费月份与理财推荐句式，仍未接入外部LLM。

## 未改变的冻结边界

推理与执行分离、Blackboard 权威、确定性 Scheduler、适配器银行接入、Gateway 唯一访问路径、精确授权哈希、执行后核验及失败关闭均保留。ECDSA 与 Merkle 已实现并本地验证；DID、真实区块链和 ZKP 仅有接口。真实银行、原生 App、IM 或财富购买等资金业务未实现。

## 本地实现选择

- Python 标准库后端、SQLite、原生 HTML/CSS/JavaScript 前端，降低本地启动依赖。
- CNY 唯一支持币种，金额为整数分，输入最多两位小数。
- 三个 Agent 当前为确定性演示实现，未使用外部 LLM。运行时交接独立、签名且可审计；这不能被描述为已验证 LLM 推理质量。后续接入 LLM 也不得赋予执行能力。
- Intent Normalization 为非 Agent 的有限句式解析。未匹配句式、未解析或重名收款人等待用户。当前补全方式为新建完整请求，不在原任务中自动猜测关键字段。
- 源账户默认 `acct-demo`；如指定其他账户，必须通过银行客户归属检查。
- V1 VirtualBankAdapter manifest 要求所有写入授权；Policy 使用 `V1_CONFIRM_ALL`，所以常规转账为 CONFIRM，高风险为 STRONG_AUTH。保留 ALLOW/NOT_REQUIRED 概念，但 V1 不走无确认金融写路径。
- 高风险阈值默认 5000 元，可配置；强认证是本地 `.env` 口令，未配置则拒绝。不是生产多因素认证。
- 默认动作 900 秒、授权 300 秒、合约 60 秒；任何受保护字段变化都改变动作哈希，旧授权失效。
- 签名采用 HMAC-SHA256，共享服务中按身份/用途派生密钥。Agent 身份只在可信进程内分配；LLM 输出不能自行声称身份或指定网关执行主体。

## 安全与证明边界

- Python 同进程模块访问控制依赖程序调用边界，不构成抵抗任意代码执行的操作系统隔离。若插件或外部 Agent 运行不可信代码，应单独进程/服务隔离网关与密钥。
- 本地令牌固定客户绑定、Host/Origin 校验和无 CORS 保护沙箱接口；没有生产登录、会话吊销、TLS、限流、MFA 或多租户身份系统。
- 本地数据及密钥文件依赖当前 OS 用户权限，未配置 Windows 专用密钥保管或数据库文件加密。
- append-only SQLite triggers 阻止应用普通 UPDATE/DELETE；hash chain 检测链内历史改写。数据库管理员能绕过 triggers；没有外部可信锚点，不能独立证明尾部没有被截断或整条链没有被重建。
- payload hash 是消息内容完整性校验，不是公共可验证证明。HMAC 是可信本地服务校验，不是第三方不可否认性证明。
- 内存 Bus 没有 durable delivery/outbox；Blackboard 提供任务恢复。任务记录、审计和银行跨组件并非一个事务；银行内部扣款与账本是原子的。跨组件崩溃进入保守人工核查，避免重复扣款。
- 重启恢复不会自动执行或自动核验存在执行不确定的交易；人工核查 UI/工作流只显示状态，未实现人工处置与冲正工具。
- 并发别笔交易改变余额时，核验可能进入 MANUAL_REVIEW。这是严格核验当前余额的保守结果，不等于交易必然错误。
