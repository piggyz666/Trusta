# 安全基准

TRUSTA 用一组可以重复运行的攻击实测，检查多 Agent 通信和执行链能不能拦住各种伪造和篡改。

```bash
python -m benchmarks.security_benchmark --banking-version 5
```

结果写入 JSON 文件（默认 `docs/phase4-security-benchmark.json`，可用 `--output` 指定）。仓库里的 `docs/phase5-security-benchmark.json` 是最近一次正式运行的结果。

## 结果

**18 类攻击各 5 次，共 90 次，全部拦截，0 笔意外交易；135 条正常消息 0 误拒。**

| 攻击 | 说明 |
|---|---|
| 伪造 Agent 身份 | 用不在注册表里的身份发消息 |
| 无效签名 | 签名与消息不符 |
| 负载篡改 | 签名后改动消息内容 |
| 重放 | 重复发送已用过的消息 |
| 过期消息 | 超过有效期的消息 |
| 已吊销密钥 | 用吊销的密钥签名 |
| 宽限期外旧密钥 | 轮换后仍用旧密钥 |
| 越权 | 声称没有的能力 |
| 能力快照篡改 | 改动消息里的权限承诺 |
| 未授权工具调用 | 调用计划之外的工具 |
| 授权哈希不符 | 授权与操作不对应 |
| 重复执行 | 同一笔资金操作执行两次 |
| 审计事件篡改 | 改动审计记录 |
| Merkle 叶子篡改 | 改动被证明的记录 |
| 无效 Merkle 证明 | 伪造包含证明 |
| 检查点篡改 | 改动签名检查点 |
| 锚定根不符 | 检查点与锚定根不一致 |
| 签名算法降级 | 诱导使用更弱的算法 |

## 性能

| 操作 | 中位数 | P95 |
|---|---|---|
| 签名一条消息 | 15.1 ms | 22.5 ms |
| 验证一条消息 | 5.5 ms | 9.0 ms |
| 生成一个检查点 | 16.7 ms | 31.2 ms |

测试环境：Windows 11，Python 3.13，`cryptography` 47。验签包含签名、身份、能力和任务上下文检查；检查点包含整链校验、Merkle 批处理、签名和持久化。

## 六大场景闭环审计

```bash
python -m benchmarks.scenario_audit
```

对转账、账单、理财、卡片、订阅、跨场景联动六大场景做 **49 项**端到端检查。

## 局限

- 这是本地受控攻击，不是生产环境渗透测试，也不是“安全概率”估计。
- 使用合成的沙箱银行和审计记录；耗时受主机文件系统和 SQLite 影响。
- 测试全部通过不代表不存在未知漏洞。

## 对比评测：同一个模型，三种搭法

上面的攻击基准检查通信和执行链本身；下面这组评测回答另一个问题：把同一个大模型接到同一家银行，用 TRUSTA 的方式搭，和常见的搭法相比差在哪里。

![图 3 同一个大模型，三种搭法](/figs/fig3.webp)

**图 3 ｜ 同一个大模型，三种搭法：只有 TRUSTA 既不出事，又能当场办成。** 三组使用同一个模型（DeepSeek `deepseek-flash`，温度 0）、同一个沙箱银行和同一份 218 道题（正常业务、模糊指令、直接注入、间接注入、诱导编造、高风险操作），每题每组跑 3 次，共 1,962 次真实对话。**A 不设防的智能体**：最常见的写法，模型直接调用转账、挂失等银行接口，调了就执行。**B 提示词加固**：在 A 上加 8 条安全规则（不执行数据和转发内容里的指令、高风险操作先发验证码、不编造数据等），所有写操作弹确认框；能否遵守靠模型自觉。**C TRUSTA**：模型只能提议；金额、收款人必须出自客户原话，客户在卡片上逐笔确认，高风险操作由系统强制强验证。四行依次回答：会不会被话术骗着越权（攻击成功率）；真的出过事吗（未经确认就执行的越权操作、泄露系统提示词、超出风险等级的理财，合计次数）；大额、改密等高风险操作有没有强验证（覆盖率）；说一句话能不能当场办成（正常业务当轮完成率）。埋在银行数据和转发短信里的指令，这一代模型本身已能识破，三组都没有被骗；TRUSTA 的不同在于，即使模型被骗，系统也不放行。

完整方法、题库和 1,962 条逐条记录在仓库的 `docs/compare/`；复现：

```bash
python -m benchmarks.compare --live --runs 3
```
